## Purpose

`docs/frontend-source-lock.json` is the frozen manifest of frontend source
hashes that `scripts/check_frontend_lock.py` verifies, and CI runs it on every
push. The lock has been stale since 2026-09-16 because legitimate work landed
afterwards, so the check fails today (`LAUNCH_STATE.md`, B-1). The repair rule
is that the lock is **not** regenerated by blessing whatever is on disk: every
drifted file must first be traced to the commit(s) that changed it and judged
LEGITIMATE or NEEDS REVIEW. This document is that trace for the drift that was
committed before the audit began. The knowledge-encyclopedia feature that was
uncommitted when the audit began (and was committed while it ran) is traced to
its commits but deliberately **not judged** here, as instructed; the two edits
still uncommitted at the snapshot are listed as IN-FLIGHT.

## Method

Exact commands run from the repo root (Git Bash, Python 3):

```
# 1. provenance
git log --format='%h %ci %s' -- docs/frontend-source-lock.json

# 2. the checker as CI runs it (exit 1, one line: "Frontend changed: <paths>")
python scripts/check_frontend_lock.py

# 2b. same walk, same exclusions, same hashing as the checker, but split into
#     modified / added / missing (the checker prints only a flat list)
python - <<'EOF'
import hashlib, json, os
from pathlib import Path
root = Path(".").resolve()
expected = json.loads((root / "docs/frontend-source-lock.json").read_text(encoding="utf-8"))
actual = {}
for base, dirs, files in os.walk(root / "frontend"):
    dirs[:] = [d for d in dirs if d not in {"node_modules", "build", ".cache", ".vite", "coverage", ".git", "lab"}]
    for name in files:
        p = Path(base) / name
        rel = p.relative_to(root / "frontend").as_posix()
        if name == ".env" or (name.startswith(".env.") and not name.endswith(".example")) or name.endswith(".log"):
            continue
        actual[rel] = hashlib.sha256(p.read_bytes()).hexdigest()
print("modified", sorted(p for p in actual if p in expected and actual[p] != expected[p]))
print("added   ", sorted(p for p in actual if p not in expected))
print("missing ", sorted(p for p in expected if p not in actual))
EOF

# 3. committed vs in-flight, per drifted path
git diff --quiet HEAD -- frontend/<path>        # exit 0  -> identical to HEAD
git ls-files --error-unmatch frontend/<path>    # exit !0 -> untracked (new, uncommitted)
#   COMMITTED  = tracked AND identical to HEAD
#   IN-FLIGHT  = differs from HEAD OR untracked

# 4. commits that changed each path since the lock, and whether it existed at the lock
git log --format='%h %cs %s' 54886e4..HEAD -- frontend/<path>
git cat-file -e 54886e4:frontend/<path>
git show --format= --numstat                    <commit> -- frontend/<path>
git show --format= --numstat --ignore-cr-at-eol <commit> -- frontend/<path>   # real change vs CRLF/LF flips
git show --format= --unified=1 [--ignore-cr-at-eol] <commit> -- frontend/<path>

# 5. checker coverage / CI
grep -rn check_frontend_lock .github/
git log --format='%h %cs %s' -- scripts/check_frontend_lock.py
git ls-files frontend/lab | wc -l ; git ls-tree -r --name-only 54886e4 -- frontend/lab | wc -l

# generated outputs: producers read from frontend/package.json "scripts" and frontend/scripts/
```

Because the tree was changing, the final classification (steps 2b, 3, 4 and the
checker) was re-run in a single script invocation so that HEAD, `git status`,
the drift sets and the per-path commit logs all describe the same instant
(the snapshot above).

Classes used below:

- **MODIFIED**: in the lock, on disk, hash differs.
- **NEW**: on disk, not in the lock.
- **DELETED**: in the lock, not on disk.
- **GENERATED**: one of `public/sitemap.xml`, `public/robots.txt`,
  `public/fonts.css`, `src/dark.generated.css` (see "Checker gaps" for the
  producers).
- **LAB**: under `frontend/lab/` (excluded by the checker since `1474afd`).
- **IN-FLIGHT**: working tree differs from HEAD, or untracked. Not judged.

Verdict rule: **LEGITIMATE** only if every content change in the file is
described by the message (subject or body) of a commit in `54886e4..HEAD` that
touched that file; **NEEDS REVIEW** otherwise (a change with no commit, or a
commit whose message does not cover that file/area).

## Checker gaps

Facts about `scripts/check_frontend_lock.py` (last changed `1474afd`,
2026-09-20) and how it is used. Nothing here was changed by this audit.

1. **Generated outputs are locked by their output hash.** The checker does not
   exclude them, and the lock contains all four:
   - `public/sitemap.xml` and `public/robots.txt` are written by
     `frontend/scripts/generate-sitemap.js`, which `frontend/package.json`
     runs on every build (`"prebuild": "npm run check:opacity && npm run
     check:seo && npm run sitemap"`). The script stamps every `<lastmod>` with
     `new Date().toISOString().slice(0, 10)` and fetches insights/case studies
     from the API, so its output is not deterministic: any local `npm run
     build` on a new day dirties `sitemap.xml` with no source change, which is
     exactly what `5b441aa` committed and what is in-flight now.
   - `public/fonts.css` is written by `frontend/scripts/fetch-fonts.py`;
     `src/dark.generated.css` by `frontend/scripts/gen-dark.py`. Both
     generators are themselves in the lock, so locking their outputs is
     redundant while generation is deterministic and misleading when it is not.
2. **CI runs it, and CI is red because of it.** `.github/workflows/check.yml`
   runs `python scripts/check_frontend_lock.py` on `push` and `pull_request`,
   after `pytest` and `npm ci` and **before** `npm run lint && npm test &&
   npm run test:build && npm run build` and the raw-metadata check. While the
   lock is stale the job fails at that step, so none of the later checks
   produce a signal on any push (`LAUNCH_STATE.md`, B-1). Because the checker
   runs before `npm run build`, CI never sees the sitemap regeneration that a
   local build produces; local and CI results can differ for that file.
3. **No regeneration mode.** The script has no `--write`, `--update`, or any
   flag (no `argparse`, no `sys.argv`), and no other script in the repository
   writes `docs/frontend-source-lock.json` (repo-wide grep finds only the
   checker, `.gitattributes`, and docs). The lock has only ever been written by
   hand-run code (`5e7d32a`, `54886e4`).
4. **Output is a single line with no classification.** It prints
   `Frontend changed: ` + a comma-joined list, with no modified/added/missing
   split and no indication of which lock commit it is checking against. The
   split in this audit needed the reproduction script in the Method.
5. **Line endings are preserved but not policed.** `* -text` keeps bytes
   stable across OSes (good for hashing) but disables normalisation, and the
   tree is inconsistent: of the 30 cleared drift files, 14 are CRLF-only, 11
   are LF-only and 5 are mixed at HEAD (`src/components/Nav.js`,
   `src/components/NextSteps.js`, `src/lib/motion.js`,
   `src/pages/home/WhatWeDoGrid.js`, `src/story.css`). Four commits since the
   lock flipped line endings on lines they did not otherwise touch (`3f531b3`
   Home.js 140/140 raw vs 10/10 real; `b656dc6` App.css 193/171 vs 22/0;
   `a3e4692` Work.js 89/89 vs 1/1; `616cfc8` Contact.js 16/16 vs 2/2). An
   editor that normalises on save will produce lock drift with no source
   change, and inflated diffs hide the real change during review.
6. **Coverage is `frontend/` only.** `frontend/scripts/` and
   `frontend/public/` are covered (both have lock entries and are walked). The
   deploy-boundary files ADR-001 relies on (`vercel.json` `buildCommand`
   copying `lab` into `build/lab`; `amplify.yml` `cp -r lab build/lab`) and
   the checker itself are outside the walk and unlocked.
7. **`frontend/lab/` is excluded and nothing else verifies it.** Per ADR-001
   the Lab cannot be rebuilt from this repo, so the 72 committed files have no
   integrity check at all once excluded. That is the intended boundary, not a
   defect of this lock, but it is a gap in tooling.

## Regeneration command

`scripts/check_frontend_lock.py` has **no** `--write`/`--update` flag or
equivalent, and no regeneration script exists in the repository. The lock's
current serialisation is `json.dumps(indent=2, sort_keys=True)` with CRLF line
endings and a trailing CRLF; the snippet below reproduces the current file
byte-for-byte from the current lock content (verified during this audit) and
uses the same walk, exclusions and hashing as the checker. Run it from the repo
root **only after** the preconditions in Recommendation 1 to 3 are met, then
run the checker to confirm it prints `Verified <n> unchanged frontend files.`:

```
python - <<'EOF'
import hashlib, json, os
from pathlib import Path
root = Path(".").resolve()
lock = {}
for base, dirs, files in os.walk(root / "frontend"):
    dirs[:] = [d for d in dirs if d not in {"node_modules", "build", ".cache", ".vite", "coverage", ".git", "lab"}]
    for name in files:
        p = Path(base) / name
        rel = p.relative_to(root / "frontend").as_posix()
        if name == ".env" or (name.startswith(".env.") and not name.endswith(".example")) or name.endswith(".log"):
            continue
        lock[rel] = hashlib.sha256(p.read_bytes()).hexdigest()
text = json.dumps(lock, indent=2, sort_keys=True).replace("\n", "\r\n") + "\r\n"
(root / "docs/frontend-source-lock.json").write_bytes(text.encode("utf-8"))
print(len(lock), "entries written")
EOF
python scripts/check_frontend_lock.py
```

If generated outputs are excluded per Recommendation 4, add their paths to the
skip condition in both the checker and this snippet before regenerating, so the
lock and the checker agree.

### Decision on generated files

Recommendation 4 offered two routes. The inputs route was taken: every
generated file stays in the lock, because each is now deterministic from
committed inputs.

- `public/sitemap.xml`: `generate-sitemap.js` writes `lastmod` from
  `scripts/sitemap-lastmod.json`, a committed fingerprint manifest, and moves
  a date only when a page's fingerprint moves. Two consecutive builds produce
  identical output (`lastmod moved for 0`). Insights and case studies fall
  back to the checked-in snapshot, so a build without the API lists the same
  URLs as a build with it.
- `public/robots.txt`: rewritten on every build with the same `Sitemap:` line.
- `public/fonts.css`, `src/dark.generated.css`: written by hand-run scripts
  that are themselves locked; regenerate and commit together with the
  generator.
- `scripts/content-snapshot.json`: regenerated from the seed;
  `tests/test_api.py` fails when it and the seed disagree.

A build can therefore no longer dirty the lock without a source change, which
is the property the lock exists to give CI.

`scripts/check_frontend_lock.py` now prints modified, added and missing paths
separately, accepts `--write` to regenerate (same walk, exclusions and
